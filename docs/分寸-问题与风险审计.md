### 1.1 当前最可信的 5 个论点
1. 主方向选择正确——文案审核是四个方向中唯一能在赛程内形成真实闭环的。
2. "候选判断 + 二选一解释 + 用户确认"的机制设计，直接击中"学判断 vs 学措辞"的分水岭。
3. 四段式结果（问题句 → 冲突标准 → 历史依据 → 建议）是清晰、可验证的输出格式。
4. 反馈动作压缩为 4 个按钮，把数据采集嵌在用户本来就要做的审稿动作里。
5. 团队自己已经识别出"提示词 + 知识库"风险和"修改稿代表性"风险，说明对难点的理解到位——这本身就是过程记录的素材。

### 1.2 最薄弱的 5 个论点
1. 没有任何真实数据，一切都是案例设想。
2. "例外不污染标准"没有机制，只有承诺。
3. "持续价值"只有期望曲线，没有指标定义和采集方式。
4. "换团队换结果"的 A/B 记忆如果手写，会被一眼识破。
5. 一个月后的长期价值无法在比赛期间验证，但目前的叙事把它讲得像已经成立。

### 1.3 必须补证的 5 个证据
1. ≥3 组真实原稿/修改稿（队员自己的文案）。
2. 两套由真实修改自动提取生成的 A/B 记忆（附提取日志）。
3. 至少一次真实发生的"系统误判 → 用户纠正 → 再审证明生效"记录（带时间戳）。
4. 至少一次真实发生的"标记例外 → 再审同类稿规则仍生效"记录。
5. 逐轮的人工解释次数 / 重复问题数 / 接受率原始数据（哪怕只有 2–3 轮）。

### 1.4 经审核后核心定位（≤120 字）
> 分寸把一位负责人在真实修改中反复做出的判断，经确认后沉淀为带条件、带来源、可推翻的团队审核记忆，并在下一篇文案中逐句给出依据。同一稿件在不同团队记忆下结论不同；判断错了可当场纠正，例外不污染标准。

## 2. 红队 15 问

分类：🔴 致命（答不好直接出局）/ 🟠 重要（影响名次）/ 🟢 可解释（准备好即可）

### 🔴 致命

**Q1. 这和"提示词 + RAG"有什么区别？我把历史稿子直接丢给 GPT 不就行了？**
- 评委为什么问：这是本赛道所有项目的第一道门。
- 最诚实的回答：如果只是"上传 → 提规则 → 审"，确实没区别。区别在四个代码层机制：① 候选判断必须经用户确认并选择解释，模型输出不直接进审核链路；② 范围过滤是确定性代码，不是提示词里的一句话；③ 例外单独存储，不改规则本体；④ 模型引用的规则 ID 被后端校验，编不出来源。RAG 检索的是相似文本，分寸检索的是"你确认过的判断 + 边界"。
- 还缺什么证据：对照实验第二组（只喂历史文案）的实际输出。
- 30 秒证明：切到 P5 对照页，左边显示"直接把 5 篇历史稿 + 新稿给模型"的结果，右边分寸结果；指出左边无法说明"你哪次修改确认了什么"，也无法处理"报名提醒不适用"。
- 无法证明时：删掉"护城河"字眼，改说"这是我们认为形成护城河的机制，比赛期间验证了它能跑通"。

**Q2. 一次修改凭什么代表长期标准？可能只是客户当天的临时意见。**
- 评委为什么问：这是数据资产是否真实的根本。
- 最诚实的回答：不能代表。所以系统提取的只是"候选判断"，用户必须四选一：长期 / 仅当前项目 / 这次例外 / 暂不记录。只有"长期"进入通用审核链路。真正让它变成标准的不是那一次修改，而是后续多次审核中被接受的记录（`stats.accepted`）。
- 还缺什么证据：一条规则被多次接受的真实记录。
- 30 秒证明：点开记忆库任一规则，展示 `confirmation` + `stats.applied/accepted` + `feedback_log`。
- 无法证明时：把"沉淀标准"改为"沉淀待验证的判断，并持续跟踪它是否成立"。

**Q3. 你的数据壁垒到底在哪？规则我也可以手写一份。**
- 评委为什么问：手写规则文档确实存在，为什么需要你。
- 最诚实的回答：手写规则丢掉的是三样东西：① 规则来自哪次修改的原文对照（新人看规则不理解，看修改秒懂）；② 规则被拒绝、标例外、改范围的历史；③ 哪些规则实际被接受、哪些形同虚设。这三样只能从真实使用中积累，且和这个团队的稿件强绑定。
- 还缺什么证据：比赛期间积累的真实记录量（哪怕只有十几条）。
- 30 秒证明：展示同一条规则 v1 → v2 的 history 和变更原因。
- 无法证明时：改说"壁垒来自使用过程的积累，我们在比赛期间验证了积累机制可以运转"。

**Q4. 换一个团队，结果真的不同吗？还是只是禁词表不同？**
- 评委为什么问：赛道核心要求"个体差异"。
- 最诚实的回答：不同之处不只是禁词，而是判断方向可以相反。品牌 A 拦"无来源效果承诺"，品牌 B 允许强销售表达但拦"绝对化竞品比较"。同一句"比同类产品快 3 倍"在 A 被要求补来源，在 B 被要求删掉竞品比较。
- 还缺什么证据：A/B 记忆必须来自两位真实队员的真实修改。
- 30 秒证明：P5 并排对照，同一新稿，两列不同的命中。
- 无法证明时：如果 A/B 有一方是编的，如实说明"B 为演示辅助数据"。

### 🟠 重要

**Q5. 模型把修改意图归因错了怎么办？它猜"你不喜欢数字"，实际你只反对无依据的数字。**
- 最诚实的回答：会错，且我们的 Demo 就展示这个错。机制是：候选阶段强制给 2 个互斥解释让用户选；审核后用户拒绝并选"判断本身错"，规则改版，旧版进 history。
- 30 秒证明：Demo 第 5 步，用含"根据项目数据减少 32%"的新句验证不被误拦。

**Q6. 例外积累多了，规则不就名存实亡？**
- 最诚实的回答：例外只写在 `exceptions[]`，不修改 `trigger` 和 `scope`；同场景例外 ≥2 次才提议范围变更，仍需用户确认。规则本体只在用户明确选"判断本身错"或"范围不对"时才变。
- 30 秒证明：标一次例外后立即再审一篇同类型公开宣传稿，规则仍命中。

**Q7. 用户为什么愿意持续点接受/拒绝？这也是成本。**
- 最诚实的回答：因为审稿本来就要做，分寸只是把"改这句"变成"点接受/拒绝"。相比另一种沉淀方式——写品牌规范文档——成本低一个量级。但我们承认这是推断，比赛期间只能记录每轮反馈耗时。
- 30 秒证明：指标条显示每轮反馈耗时。

**Q8. 持续使用价值是口号吗？一天半能看出什么？**
- 最诚实的回答：一天半只能看趋势，不能证明规律。我们定义了三个可自动记录的指标（重复问题数、人工解释次数、接受率），现场展示实际的 2–3 轮数字，不做百分比包装。
- 30 秒证明：复审页"与上一轮对比"条。

**Q9. 规则之间冲突怎么办？"表达克制"和"活动要有紧迫感"打架。**
- 最诚实的回答：靠场景标签隔离——克制适用公开宣传，紧迫感适用报名提醒。同场景内冲突时，MVP 只做检测提示，由用户决定停用哪条。不做自动仲裁。
- 30 秒证明：记忆库中两条规则不同的 `scope`。

**Q10. 这些文案有商业敏感信息，隐私怎么处理？**
- 最诚实的回答：MVP 是本地 JSON 文件，不上传除模型 API 外的任何服务；Demo 用队员自己授权的文案。赛道"共同要求"明确要求使用授权数据，我们遵守。
- 30 秒证明：展示 workspace 文件在本地。

**Q11. 一天半真做得完吗？**
- 最诚实的回答：Must 列表是 6 个接口 + 6 个页面 + 1 个 JSON 存储，模型只有两类调用。砍掉了多智能体、插件、集成、账号、向量库。如果做不完，优先保证 P1→P2→P3→反馈→再审的单线。
- 30 秒证明：现场跑一遍。

### 🟢 可解释

**Q12. 为什么不用微调？**
- 微调学的是风格，学不到"这条规则来自哪次修改、是否有例外"；且不可推翻、不可追溯。分寸要的是可解释的结构化记忆。

**Q13. 换个行业（法律、医疗文案）能用吗？**
- 机制通用，数据不通用——这正是赛道要求的。但我们不宣称已验证，只做了一个场景。

**Q14. 为什么只做文本？为什么不接飞书？**
- 一天半只验证核心机制。接入是分发问题，不是价值验证问题。

**Q15. 你们和现有品牌一致性工具（如 Writer、Grammarly Business）的区别？**
- 它们要你先写规范；分寸从你的修改里长出规范，并记录规范被推翻和例外的过程。

## 3. 是否建议参赛当前版本

**建议参赛，但附带两个硬条件：**

1. **开工两小时内拿到 ≥3 组真实原稿/修改稿。** 拿不到，当前版本不建议参赛——一个虚构品牌的演示在"数据壁垒"和"产品可用性"两项上会同时失分，且"过程记录"无从谈起。
2. **范围过滤、例外隔离、rule_id 校验、日志落盘四件事必须做在代码层。** 只做在提示词里，Q1 无法回答，项目会被归类为"提示词 + 知识库"。

满足这两个条件，当前版本在本赛道有竞争力：方向选择准确、机制设计已经触及难点、演示闭环可在赛程内跑通。不满足，建议缩小到"只演示学习闭环机制本身"，并诚实说明数据为演示辅助数据。

### 特别检查
- ❌ 不要把"记住规则"写成"理解判断" → 统一用"沉淀经确认的判断"
- ❌ 不要把"有修改记录"写成"有数据壁垒" → 壁垒来自"记录 + 确认 + 反馈 + 版本"的积累，比赛期间只能展示积累机制
- ❌ 不要把"用户可以反馈"写成"用户会持续使用" → 只报实际反馈耗时和次数
- ❌ 不要把预置答案写成实时能力 → 现场必须接受评委改一句文本
- ❌ 不要把一次成功案例写成普遍效果 → 所有数字前加"本次演示中"
