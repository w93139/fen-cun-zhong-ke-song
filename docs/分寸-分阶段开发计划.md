# 「分寸」分阶段开发计划

> 生成日期：2026-09-12 · 阶段四 Step 5 + 阶段六执行协议
> 前提：方案经团队确认后才开始编码。每个阶段按固定顺序：目标与不做 → 文件与数据结构 → 阶段文档 → 最小可运行 → 自动测试/构建 → 本地浏览器验收 → "照着点"清单 → 已知问题与证据状态。
> 时间预算 [假设]：Day1 约 10 小时（含数据生成），Day2 上午约 4 小时。总计 14 小时。

详见《无历史数据验证方案》第 2 节。产出：3 份原稿、3 份 B 修改稿（含理由）、2 份 C 修改稿（含理由）、3 份新方案。先存为纯文本文件放 `data/raw/`，P2 完成后通过界面导入。

## P1 可运行骨架

**目标**：一条命令启动，浏览器打开首页看到两个工作区，后端能读写工作区 JSON。
**不做**：任何模型调用；任何业务逻辑。

**文件**
```
backend/app/main.py                 FastAPI 入口、挂载 static、统一错误处理
backend/app/core/config.py          读 .env（pydantic-settings）
backend/app/core/storage.py         load/save 工作区（原子写入 + 备份）、append_log
backend/app/schemas/workspace.py    Workspace/Rule/DocPair/ReviewRun/Finding Pydantic 模型（schema_version=1）
backend/app/api/workspaces.py       GET /api/workspaces, GET /api/workspaces/{ws}/rules
backend/app/static/index.html       壳：顶栏工作区切换 + 6 个视图占位
backend/tests/test_storage.py
backend/requirements.txt  .env.example  .gitignore  README.md
data/workspaces/reviewer_A.json  reviewer_B.json（空规则）
```

**测试**：原子写入（写入中断不破坏原文件）；schema_version 缺失时拒绝加载；备份文件生成。
**验收（照着点）**：
- [ ] 终端运行 `uvicorn app.main:app --reload`，无报错
- [ ] 打开 `http://127.0.0.1:8000`，看到"评审人 A / 评审人 B"切换
- [ ] 打开 `/docs`（Swagger），`GET /api/workspaces` 返回两个工作区
- [ ] 手动把 `reviewer_A.json` 改坏（删一个括号），刷新页面看到友好错误而非堆栈
**证据状态**：无业务证据；工程底线（密钥、原子写入、统一错误）已落实。

## P2 核心闭环

**目标**：真实原稿/修改稿 → diff → 候选（#1）→ 用户确认 → 新方案审核（#3）→ 四段式卡片，含 rule_id 校验与"加载 N/跳过 M"。
**不做**：反馈更新记忆（P3）；反方验证（P4）；对照（P4）。

**文件**
```
backend/app/services/diff.py           句切分 + difflib 对齐 → [{sentence_id, before, after}]
backend/app/services/llm.py            单一模型客户端：超时、重试 1 次、宽容 JSON 提取、Pydantic 校验
backend/app/services/prompts/extract.md  review.md
backend/app/services/pipeline.py       import_doc / extract_candidates / resolve_candidate / review
backend/app/services/rules.py          filter_rules_by_scope / validate_rule_refs / build_evidence
backend/app/api/docs.py  candidates.py  review.py
backend/app/static/index.html          导入视图、候选确认视图、审核视图
backend/tests/test_diff.py  test_llm_parse.py  test_rules_filter.py  test_pipeline_mock.py
```

**关键实现约束**
- `filter_rules_by_scope` 与 `validate_rule_refs` 是纯函数，不接触模型。
- 审核视图顶部必须显示 `rules_loaded` / `rules_skipped(why)`。
- 候选确认视图每条候选显示：statement、2 个解释（各带 would_flag / would_pass 例句）、建议 scope（可改）、四选一按钮。
- 手动新建规则入口存在且记 `manual.explanation`。

**测试（mock）**：diff 对齐 3 个样例；JSON 提取兼容 code fence / 尾逗号 / 前后废话；>3 候选截断并记瑕疵；scope 过滤 5 组用例（applies / excludes / project 匹配 / inactive 不加载 / candidate 不加载）；无效 rule_id 降级为 generic；候选 → 规则字段完整。
**真实冒烟**：用 D-A-001 真实调用 #1 一次、用 N-1 真实调用 #3 一次；记录模型、耗时、首次合规与否。
**验收（照着点）**：
- [ ] 粘贴 D-A-001 原稿+修改稿，选"上线前 PRD"，点导入 → 看到 diff 表
- [ ] 点"提取候选" → 10–20 秒内看到 ≤3 条候选，每条有两个解释和例句
- [ ] 对一条候选：选解释②、范围勾"上线前 PRD"、点"长期适用" → 记忆库出现 R-A-001 v1，展开能看到 before/after 原文和"你选择的解释"
- [ ] 粘贴 N-1，选"上线前 PRD"，点审核 → 顶部显示"加载 1 条，跳过 0 条"；无基线的指标句被标；有基线的句子未被标
- [ ] 点开一条发现 → 看到 问题句 / 冲突规则 R-A-001 v1 / 历史依据（原文）/ 建议
- [ ] 把 N-1 中一句改掉重新审核 → 结果变化
- [ ] 关掉模型 Key 重试 → 看到"模型暂时不可用"，页面不崩
**证据状态**：可用性 ✅（真实输入跑通）；数据壁垒 ◐（可追溯，但未有 A/B）；过程记录 ◐（日志有）；持续价值 ✗。

## P3 规则与反馈持久化

**目标**：四类反馈真实改变记忆；版本、例外、停用、日志、逐轮指标全部落地。
**不做**：反方验证；对照；scope 提案自动生成（P4）。

**文件**
```
backend/app/services/feedback.py    apply_feedback：accept / reject(reason) / exception / adjust_scope
backend/app/services/metrics.py     compute_metrics(workspace) 逐轮
backend/app/api/feedback.py  metrics.py  log.py
backend/app/static/index.html       发现卡片四按钮 + 拒绝原因三选一；记忆库版本历史；日志视图；指标条
backend/tests/test_feedback.py  test_metrics.py
```

**关键实现约束**
- `reject(判断本身错)` → 弹出"用一句话说明你反对的是什么"（可跳过；填写则记 `manual.explanation`）→ 规则 version+1，新 statement 由用户文本或模型改写（模型改写需再确认）。MVP 简化：用户直接编辑 statement 文本。
- `reject(范围不对)` / `adjust_scope` → scope 变更 → version+1。
- `reject(这次特殊)` → 转为 exception 路径。
- `exception` → 只追加 exceptions[]，**断言 statement/trigger/scope 未变**（测试用例）。
- 同 scene 例外 ≥2 → 写入 `scope_change_proposal`（P4 才在 UI 展示为候选，P3 只落数据）。
- 每个动作写 `finding.feedback` + 对应规则事件。

**测试**：例外不改本体（核心用例）；拒绝生成 history 且 version+1；inactive 后不被加载；metrics 逐轮计算正确（含负数差值）；`manual.explanation` 计数正确。
**真实冒烟**：走验证方案第 5–8 步一遍。
**验收（照着点）**：
- [ ] 对一条发现点"拒绝"→"判断本身错"→ 改写 statement → 记忆库该规则显示 v2，展开"版本历史"看到 v1 和变更原因
- [ ] 再审一份含同类句子的方案 → 按 v2 判断
- [ ] 粘贴 N-2（探索期），一条发现点"这次是例外" → 记忆库该规则 version 不变，"例外 1 条"
- [ ] 粘贴 N-3（上线前 PRD）→ 同一规则仍命中
- [ ] 打开日志视图 → 看到上述每一步的时间线
- [ ] 打开指标条 → 看到第 1/2/3 轮的人工解释次数、接受/拒绝/例外数
**证据状态**：可用性 ✅；数据壁垒 ◐（单工作区可追溯、可推翻、例外隔离）；过程记录 ✅（真实误判→纠正日志）；持续价值 ◐（有逐轮数字）。

## P4 增强

**目标**：反方验证(#2)；A/B 对照视图；scope 变更提案进入候选确认。
**不做**：任何新页面类型；任何新数据实体。

**文件**：`prompts/counter.md`、`pipeline.extract_candidates` 加 #2 步（失败静默降级）、`api/compare.py`、index.html 对照视图。
**测试**：#2 失败时候选仍返回且 `counter_checked=false`；compare 不写入工作区。
**真实冒烟**：#2 一次；compare 一次（N-1 在 A/B）。
**验收（照着点）**：
- [ ] 提取候选时看到每条多一行"反方检查：可能过度泛化 / 未发现"
- [ ] 对照视图粘贴 N-1 → 左右两列，至少一句结论不同
- [ ] 若某规则在同一场景标了 2 次例外 → 候选确认页出现"建议把 X 加入排除范围"的提案
**证据状态**：数据壁垒 ✅（换评审人换结论）。

## 每阶段结束时产品经理必须确认的 5 个问题

1. 实际界面是否符合"评审人在审一段指标章节"这个任务？
2. 系统是否展示了正确来源（before/after 原文 + 我选的解释）？
3. 我拒绝一条判断后，规则是否真的变了（版本号、再审结果）？
4. 我标一次例外后，规则本体是否没变、范围内文档是否仍被拦？
5. 评委看 10 秒能否看懂一张发现卡片？

## 范围与组件反审计（防扩张）

若开发中出现以下任一情况，立即暂停并执行反审计：
- 想加第 7 个视图 / 第 4 类模型调用 / 任何数据库 / 任何前端框架；
- 想让模型"自动决定"任何本应由用户确认的事；
- 想在 P3 未验收前做 P4/P5；
- 想在闭环未跑通前做视觉。

反审计问题：它服务哪个用户动作？对应哪个评分证据？没有它会失去什么？能否更简单？能否在比赛前验收？答不全 → 移到"未来扩展"。
