# 「分寸」无历史数据验证方案

> 生成日期：2026-09-12 · 阶段三产出
> 前提：当前没有任何历史数据。所有数据由团队成员在比赛期间**真实产生**，全部标记 `data_origin: "live"`。
> 答辩表述：**"分寸通过几次真实的方案修改，在现场形成并验证最小审核记忆。"**

---

## 1. 角色分配

| 角色 | 谁 | 做什么 | 不做什么 |
|------|----|--------|---------|
| 方案作者（Author） | 队员 A | 写 3–4 段 AI 产品方案的「指标与验收标准」章节（每段 8–15 句），刻意保留日常 PRD 中常见的写法（含无基线的百分比、方向性表述、模糊负责人） | 不迎合评审人、不故意埋错 |
| 评审人 α（Reviewer α） | 队员 B | 以真实上线评审人的身份修改 A 的稿子，每处修改写一句理由（≤20 字）；后续作为工作区 `reviewer_A` 的用户操作确认与反馈 | 不看队员 C 的修改 |
| 评审人 β（Reviewer β） | 队员 C | 对**同一批原稿**独立修改，按自己的标准；作为工作区 `reviewer_B` 的用户 | 不看队员 B 的修改 |
| 记录员 | 开发中的系统 | 保存原稿、修改稿、逐条理由、修改者身份、时间戳 | — |

> [待确认] 三人分工假设。若只有两人，队员 A 同时担任评审人 β（对自己写的稿子按"另一种标准"修改会失真，需在答辩中如实说明）。

## 2. 数据生成流程（目标：开工后 2 小时内完成）

| 步骤 | 时长 | 产出 | 记录 |
|------|------|------|------|
| S1 队员 A 写原稿 ×3（不同 AI 产品主题，如：智能客服意图识别 / 文档摘要助手 / 销售线索评分） | 30 min | `D-A-001/002/003.original`（同一原稿同时用于 β，故只写一份） | 保存为 doc，`author`, `scene` 标签由 A 定：2 份"上线前 PRD" + 1 份"探索期方案" |
| S2 队员 B 修改 ×3 并逐条写理由 | 30 min | `D-A-00x.revised` + `change_notes` | `reviewer: 队员B` |
| S3 队员 C 独立修改同一批原稿 ×2（至少 2 组）并写理由 | 20 min | `D-B-001/002.revised` | `reviewer: 队员C`，导入工作区 `reviewer_B` |
| S4 队员 A 再写 3 段**新方案**用于审核轮次（不给 B/C 看） | 30 min | `N-1`（上线前 PRD，含 1 句有基线的指标 + 1 句无基线的）、`N-2`（探索期方案，含方向性表述）、`N-3`（上线前 PRD，含方向性表述 + 1 句竞品比较） | 标记 `data_origin: live`，审核时才导入 |

**止损点**：2 小时后不足 3 组 → 用团队自己的「分寸」思路文档作为补充样本（思路文档 1 的定位句 → 思路文档 2 的收紧版是一次真实的方案→修改，属于 AI 产品方案范畴，`reviewer` 记为写第二份文档的人）。仍不足 → 缩减为 2 组 + 1 个工作区，Demo 中如实说明。

## 3. 验证闭环（九步，对应新提示词第三阶段）

| 步 | 系统动作 | 用户动作 | 验证什么 | 通过标准 | 记录 |
|----|---------|---------|---------|---------|------|
| 1 | 导入 D-A-001（原稿+修改稿+理由），生成 diff | 队员 B 选场景"上线前 PRD" | 输入可被接收 | diff 正确对齐 ≥80% 修改句 | `doc.imported` |
| 2 | 提取候选(#1) + 反方检查(#2)，展示 ≤3 条候选，每条 2 解释 + 反例预演 | 无 | 候选是否合理 | ≥1 条候选被 B 认为"是我的意思" | `extract.succeeded`，候选原文 |
| 3 | — | B 对每条候选：选解释、选范围、四选一（长期/项目/例外/不记录） | 候选≠规则 | 至少 1 条长期规则生成，且选中解释 ≠ 模型第一个解释（证明用户在选择，不是点确认）——若恰好全选第一个，如实记录 | `candidate.resolved`，`rejected_intent` |
| 4 | 导入 N-1，scope 过滤，审核(#3)，展示 findings + "加载 N/跳过 M" | B 看结果 | 有依据的审核 | 无基线句被标，有基线句通过；每条 memory finding 有存在的 rule_id | `review.succeeded`，`invalid_rule_refs` |
| 5 | — | B 接受/拒绝各条 | 反馈可采集 | 至少 1 条接受 | `finding.feedback` |
| 6 | 若模型初始把规则学成"不允许百分比"（预期会发生，若未发生则跳到 7 并如实说明） | B 拒绝并选"判断本身错"，系统展示 v1→v2 变更 | 可推翻 | 规则 version=2，history 有 v1 | `rule.version_bumped` |
| 7 | 导入 N-2（探索期方案），审核 | B 对"显著提升"被拦 → 点"这次是例外"（或系统因 scope 已排除探索期而未拦——两种结果都记录） | 例外记录 | exceptions[] +1，version 不变 | `rule.exception_added` |
| 8 | 导入 N-3（上线前 PRD），审核 | B 看 | 例外不污染 + 纠正生效 | 方向性表述在上线前 PRD 中仍被拦；有基线的指标仍通过 | `review.succeeded`，对比 run 指标 |
| 9 | `/api/compare` 同时用 reviewer_A 和 reviewer_B 审核 N-1 | 无 | 换评审人换结论 | 两个工作区 findings 至少 1 条不同（不同 rule 命中或同句不同结论） | `compare.run` |

**每步的证据**都由日志自动落盘，Demo 日志页直接展示。

## 4. 硬性要求对照

| 新提示词要求 | 落实方式 |
|-------------|---------|
| 至少 3 组真实原稿/修改稿 | S1–S3 产生 3（A）+ 2（B）组 |
| 不得手写规则伪装成历史学习 | 规则只能通过 `/extract` → `/resolve` 产生；`/rules` 手动新建端点会记 `manual.explanation` 事件并在记忆库中显示"手动创建"标签，Demo 中不隐藏 |
| 每条规则有 rule_id、来源版本、确认状态、适用范围、例外、有效性、版本记录 | 数据模型全部字段（见架构文档 4.3），API 层 Pydantic 校验缺一不可 |
| 反馈至少支持接受、拒绝、例外、调整范围 | `/feedback` 四种 action |
| 拒绝不等于删除，保留可追溯版本 | 无 DELETE；拒绝 → version+1 + history；停用 → inactive |
| 例外不得直接修改长期规则本体 | 例外只写 `exceptions[]`；代码层禁止 exception 分支触碰 statement/trigger/scope；pytest 有专门用例 |

## 5. 指标定义与采集（必须采集，不得提前编造）

| 指标 | 定义（确定性计算） | 来源 |
|------|-------------------|------|
| 每轮人工解释次数 | 该 run 内：手动新建规则次数 + 改写候选解释文本次数 + 拒绝时填写自由文本次数 | `manual.explanation` 事件计数 |
| 接受 / 拒绝 / 例外 / 范围调整数量 | findings 中各 action 计数 | `finding.feedback` |
| 重复问题数量 | 该 run 中命中的 rule_id 在上一 run 中也命中且上一轮被接受的数量（= 系统正确重复拦截，是正向指标） | findings 交叉 |
| 规则误用数量 | 该 run 中被拒绝且原因 ∈ {判断本身错, 范围不对} 的 findings 数 | `finding.feedback` |
| 第二轮相比第一轮减少的人工解释次数 | run2.manual − run1.manual（负数表示增加，如实报） | 计算 |
| 例外是否污染后续审核 | 标记例外后的下一 run 中，同一 rule 在范围内文档是否仍命中：是=未污染 | 步 7→8 对比 |
| 模型 rule_id 无效引用率 | invalid_rule_refs / findings | `review.succeeded` |

**报告方式**：只报实际数值，如"第 1 轮人工解释 3 次，第 2 轮 1 次"；不算百分比、不说"提升 X%"。

## 6. 数据标记规范

| `data_origin` | 含义 | Demo 中如何展示 |
|--------------|------|----------------|
| `live` | 比赛期间队员真实产生（含赛前一晚的准备数据，只要是真实修改） | 默认无标签 |
| `preset` | 为保证 Demo 流畅、赛前用 live 数据跑好的结果（如已确认的规则） | 卡片角标"预置" |
| `aux` | 演示辅助（如为凑 A/B 差异临时写的例句） | 卡片角标"演示辅助"；答辩中口头说明 |

**禁止**：把 aux 或 preset 说成实时结果；把任何数据说成"历史积累"。
