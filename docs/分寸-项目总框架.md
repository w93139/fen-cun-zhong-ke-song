# 「分寸」项目总框架

> 生成日期：2026-09-12
> 依据材料：赛道说明「未定信号」（含四个参考方向）、《「分寸」：一个通过修改学会你工作标准的 AI 审稿搭档》、《「分寸」与题目匹配但需要把"抄不走/离不开"说得更硬》、《评分标准说明》
> 标注约定：**[事实]** = 材料中明确写出；**[推断]** = 基于材料的合理推断；**[假设/待验证]** = 材料未覆盖，需团队确认或实验验证

## 1. 一页纸结论

### 1.1 当前最强的价值主张

**分寸把一个团队在反复修改文案时做出的、说得清但写不全的判断，沉淀成带条件、带来源、可推翻的审核记忆，并让这份记忆在下一篇稿子里立刻接受检验。** [事实：来自思路文档 2 的收紧定位]

它对应赛道"未定信号"的核心要求：同一套系统，喂进去不同团队的修改历史，产出完全不同的审核结论。[事实：赛道说明]

### 1.2 当前最危险的 3 个问题

| # | 问题 | 为什么致命 | 状态 |
|---|------|-----------|------|
| 1 | **没有真实的原稿/修改稿** | 全部演示将变成虚构品牌的预置剧本，评委在"产品可用性"和"数据壁垒"两项直接扣分。思路文档自己已设了止损点：两小时拿不到真实修改记录就换方向。 | [待验证] 材料中没有任何一组真实样本 |
| 2 | **退化为"提示词 + 知识库"** | 如果"条件化 / 可推翻 / 可追溯"三个机制只是 UI 上的三个字段，而没有在系统行为上产生可见差异，评委一句"我把历史稿直接丢给模型不就行了"即可否掉。 | [推断] 两份思路文档都点出了这个风险，但目前没有任何机制设计细节 |
| 3 | **"持续使用价值"只有口号，没有可测指标** | 一天半最多跑 2–3 轮审核，样本极小。如果不预先定义"人工解释次数""重复问题数""接受率"的采集方式，现场只能靠嘴说。 | [事实] 评分标准要求三个指标，[推断] 目前未定义如何记录 |

次级风险：模型对"为什么改"的意图归因可能幻觉；用户反馈动作若超过 4 个选项会导致反馈成本上升；A/B 两套记忆若都是编的，"换数据换结果"演示会失去可信度。

### 1.3 是否建议继续沿用当前方向

**建议继续，但收紧到唯一主方向：专家判断复刻。** [事实：两份文档与评分标准一致]

理由：四个官方方向中，报价参谋、流失雷达、招聘校准都需要等待成交/流失/绩效结果，一天半拿不到真实反馈；只有文案审核能在比赛期间形成"人改一次 → 系统下一份稿子被检验"的真实闭环。[事实：思路文档 1]

不建议的做法：把"流失雷达"的信号监测逻辑也拿来讲。思路文档 2 提到"借用流失雷达逻辑"，但这会稀释主线，建议答辩中不提。[推断]

### 1.4 冲奖必须优先完成的 5 件事

1. **2 小时内拿到 ≥3 组真实原稿/修改稿**（队员自己的项目介绍、文章、对外文案），并由原作者本人担任"负责人"角色。拿不到即触发止损。
2. **跑通唯一闭环**：导入 → 候选判断 → 确认范围 → 审核新稿（逐句 + 依据）→ 接受/拒绝/例外 → 记忆更新 → 再审。不做第二条流程。
3. **实现"范围过滤在代码层，不在提示词层"**：规则按场景标签过滤后再交给模型，这样"例外不污染长期标准"是可验证的系统行为，而不是模型的自觉。
4. **建两套真实记忆（品牌 A / 品牌 B）**，由两位不同队员的真实修改生成，同一篇新稿并排对照。
5. **从第一次运行起就自动写迭代日志**：每次候选判断、确认、拒绝、例外、规则版本变更都落盘带时间戳，直接作为"过程记录 25%"的材料。

## 2. 项目核心定位

| 维度 | 一句话 |
|------|--------|
| **目标用户** | 需要持续审核团队对外文案的品牌/内容负责人——那个反复说"我们不这样说话"的人。[事实] |
| **核心痛点** | 同一类判断每篇稿子都要重新解释一遍，这些判断沉淀不下来，审核既交不给新同事，也交不给通用 AI。[事实] |
| **产品承诺** | 你改一次，它在下一篇稿子里按你的判断标准初审，并说得出依据来自你哪次修改；判断错了你可以当场推翻。[事实+推断] |
| **独有数据** | 不是文案本身，而是：原稿→修改稿的判断轨迹 + 用户确认的解释 + 适用范围 + 例外 + 后续接受/拒绝记录。[事实] |
| **长期依赖理由** | 一个月后，新同事按团队标准初审，负责人只处理高风险项、冲突和例外；换掉分寸等于丢掉这份被反复验证过的判断记忆。[事实：思路文档 2 的"长期价值"] |

### "不要这样讲"的错误定位

> ❌ "分寸是一个 AI 品牌文案审稿助手，上传你的品牌资料，它就能一键检查新文案是否符合品牌调性，并给出修改建议。"

**为什么会被评委认为只是通用审稿工具：**
- "上传资料 → 检查 → 建议"正是"提示词 + RAG"的标准流程，任何团队一小时能复刻；
- "品牌调性"是模糊的风格模仿，而不是可被验证的判断条件；
- 没有出现"修改轨迹""确认""例外""推翻"任何一个词，评委看不到数据壁垒从哪里长出来；
- 没有说明"第二次比第一次少解释什么"，无法证明持续价值。

正确讲法见第 8 节答辩叙事（另见《分寸-Demo与答辩方案.md》）。

## 3. 端到端产品框架

### 3.1 用户与首个具体场景

- **唯一用户角色**：文案负责人（Demo 中由提供真实修改稿的队员本人扮演）。[事实+假设：队员是否愿意提供真实文案待确认]
- **首发场景**：团队对外文案（项目介绍、产品说明、公众号/官网文案）的审核。[事实]
- **明确不做**：多人协作审批流、多语言、长文档（>3000 字）、非文本内容。[推断]

### 3.2 真实输入与输出

| 阶段 | 输入 | 输出 |
|------|------|------|
| 导入 | 原稿文本 + 修改稿文本（粘贴），场景标签（公开宣传 / 内部说明 / 活动提醒等） | 句级 diff 视图 |
| 候选判断 | diff | 3 条以内候选判断，每条附 2 个可选解释 + 建议适用范围 + 来源片段 |
| 确认 | 用户选择：解释、范围、处理方式（长期 / 仅当前项目 / 这次例外 / 暂不记录） | 记忆条目（状态 = 已确认）|
| 审核新稿 | 新稿文本 + 场景标签 | 逐句标注：问题句 → 冲突标准 → 历史依据 → 可执行建议 |
| 反馈 | 接受 / 拒绝（附 3 选 1 原因）/ 这次是例外 / 调整范围 | 记忆更新 + 日志 |
| 再审 | 又一篇新稿 | 与上次可对比的审核结果 + 本轮指标 |

### 3.3 核心用户旅程图

```
情绪 ↑
       │                                      ┌── 惊喜：它记住了，而且说得出来源
       │             ┌── 怀疑：它猜的对吗？    │        ┌── 信任：例外没有被滥用
       │  焦虑：又要 │      ┌── 释然：可以改  │        │         ┌── 依赖：只看高风险项
       │  解释一遍   │      │                  │        │         │
  中性 ├─────────────┼──────┼──────────────────┼────────┼─────────┼──────→ 时间
       │  ①触发      ②导入   ③确认           ④首审    ⑤反馈    ⑥复审      ⑦长期
```

| 阶段 | 用户在做什么 | 触点 / 界面 | 系统状态变化 | 情绪 | 痛点 | 分寸的介入点 | 采集指标 |
|------|-------------|------------|-------------|------|------|-------------|---------|
| ① 触发 | 收到同事新稿，发现"又是那个问题" | 无（产品外） | — | 焦虑、疲惫 | 同一判断说过很多遍，没有沉淀 | 让用户把上一次的原稿和修改稿丢进来，而不是重新写规范 | — |
| ② 导入 | 粘贴原稿 + 修改稿，选场景标签 | 导入页 / diff 视图 | 生成 diff 记录 `D-xxx` | 中性、略期待 | 不想写长篇复盘 | 只要求粘贴，不要求解释 | 导入耗时 |
| ③ 确认候选判断 | 看系统提出的 3 条候选，每条选解释 + 范围 + 处理方式 | 候选确认页 | 记忆条目从 `candidate` → `confirmed` / `project` / `discarded` | 怀疑 → 释然（"它问的是对的问题"） | 担心它学成"不喜欢数字"这种错误结论 | 系统提出"你是在避免无依据承诺，还是想整体克制？"这类二选一；用户选，不用写 | 候选采纳率、需要用户改写解释的次数 |
| ④ 首次审核 | 粘贴一篇新稿，看逐句标注 | 审核页（左稿右卡） | 生成 `findings[]`，每条引用 `rule_id` + `evidence` | 惊喜 / 挑剔 | 想知道"你凭什么这么说" | 每条建议展示：问题句 → 冲突标准 → 来自哪次修改 → 建议 | 命中数、有依据的命中占比 |
| ⑤ 反馈 | 逐条接受 / 拒绝 / 标例外 / 调范围 | 审核页动作按钮 | 更新 `feedback_log`、`stats`、必要时 `scope` / `validity` | 掌控感 | 反馈成本高就不做了 | 动作压缩到 4 个按钮；拒绝时 3 选 1 原因；例外不改规则 | 接受率、拒绝率、例外数、人工解释次数 |
| ⑥ 复审 | 再粘一篇新稿 | 审核页 + 本轮 vs 上轮对比条 | 例外被记录但规则未变；被推翻的规则已改版 | 信任建立 | 怕例外污染标准 / 怕纠正没生效 | 展示"上次你推翻的判断，这次的表现"；同时展示有依据数字被保留 | 重复问题数、人工解释次数变化、接受率变化 |
| ⑦ 长期 [假设] | 新同事用分寸初审，负责人只看冲突和高风险 | 记忆库页 / 对照页 | 规则版本累积、有效性维护 | 依赖 | 换工具 = 丢掉验证过的判断 | 记忆库可导出但语义绑定在本团队的修改历史上 | 负责人介入率 |

### 3.4 MVP 功能边界

**必须有（Must）**
- 工作区切换（品牌 A / 品牌 B），本质是两份独立记忆文件
- 原稿/修改稿导入 + 句级 diff
- 候选判断提取（≤3 条/次，每条 2 个可选解释）
- 确认动作：解释选择 + 场景范围 + 处理方式四选一
- 新稿审核：逐句标注，四段式结果（问题句/冲突标准/依据/建议）
- 反馈动作：接受 / 拒绝（3 选 1 原因）/ 这次是例外 / 调整范围
- 记忆库：规则列表，可展开看来源、确认、范围、例外、有效性、版本历史
- 自动迭代日志（时间戳 + 动作 + 前后状态）
- 同一稿件 A/B 记忆并排对照视图
- 本轮指标条：命中数 / 接受 / 拒绝 / 例外 / 人工解释次数

**可以有（Could）**
- 规则冲突检测（新候选与已有规则重复或矛盾时提示）
- 规则"降权而非删除"的置信度显示
- 审核结果导出为 Markdown

**明确不做（Won't）**
- 多智能体、浏览器插件、飞书/企微集成、账号体系、权限、多人协作、模型微调、向量库、自动改写全文

### 3.5 学习闭环

```
原稿 + 修改稿 ──► diff ──► [LLM] 候选判断（含 2 个解释、建议范围、来源片段）
                                    │
                                    ▼
                          用户确认：选解释 / 定范围 / 四选一处理
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
        长期规则(confirmed)   仅当前项目(project)    这次例外/暂不记录(discarded)
              │
              ▼
   新稿 + 场景标签 ──► [代码] 按 scope 过滤 active 规则 ──► [LLM] 逐句审核，必须引用 rule_id
                                                                │
                                                                ▼
                                          用户动作：接受 / 拒绝 / 例外 / 调范围
                                                                │
        ┌───────────────┬──────────────────────┬────────────────┼──────────────┐
        ▼               ▼                      ▼                               ▼
   accepted+1     rejected+1 → 原因 3 选 1    exceptions[] 追加             scope 修改
                  ├ 判断本身错 → 规则改版      （规则本体不变）              → version+1
                  ├ 范围不对 → 提议 scope 变更  同场景例外≥2 → 提议范围变更
                  └ 这次特殊 → 转为例外
                                    │
                                    ▼
                          记忆更新 + 日志落盘 ──► 下一篇新稿
```

关键设计决策（回答"为什么不是一次性生成规则"）：
1. **候选 ≠ 规则**。模型输出的只是 `candidate`，用户确认后才进入审核链路。
2. **范围过滤是代码，不是提示词**。审核时只把 `scope.applies_to` 包含当前场景标签、且 `validity.active = true` 的规则交给模型。这样"公开宣传规则不适用于报名提醒"是确定性行为。
3. **例外不修改规则本体**。例外只追加到 `exceptions[]`，同场景累积 ≥2 次才提议范围变更，仍需用户确认。
4. **拒绝 ≠ 删除**。拒绝要选原因，不同原因走不同分支，规则改版保留旧版本于 `history[]`。
5. **模型必须引用 `rule_id`**。审核输出中没有 `rule_id` 的发现被标记为"通用建议"，与"依据团队记忆"的发现在 UI 上区分显示，防止模型幻觉冒充历史依据。

### 3.6 判断记忆的数据结构

```json

  "workspace": "brand_A",
  "version": 2,
  "statement": "对外效果承诺必须附可核验来源",

  "type": "long_term",

    }
  ],
  "feedback_log": [
    { "doc": "新稿 01", "finding_id": "F-04", "action": "accept", "at": "..." },
    { "doc": "新稿 02", "finding_id": "F-09", "action": "exception", "at": "..." }

      "version": 1,

      "changed_at": "2026-09-12T11:40:00+08:00",
      "changed_reason": "用户拒绝 F-02 并选择'判断本身错'：反对的是无依据的数字，不是所有数字"
    }
  ]

```

**字段与机制对应表**

| 机制 | 字段 |
|------|------|
| 条件 | `trigger.description` + `positive/negative_examples` |
| 适用范围 | `scope.applies_to` / `scope.excludes` |
| 例外 | `exceptions[]`（不改规则本体）|
| 来源 | `evidence[]`（before/after/diff_id）|
| 时效 | `validity.active` / `superseded_by` / `last_confirmed_at` |
| 可撤销 | `history[]` 保留每个版本；`validity.active=false` 即停用，不删除 |
| 个体差异 | `workspace` 隔离；同一 `statement` 在不同 workspace 中可有相反 `type` |

### 3.7 审核结果的展示格式

每条发现固定四段式，不允许省略"依据"：

```
┌─────────────────────────────────────────────────────────────┐
│ ⚠ 第 3 句  "保证让你的工作效率提升十倍"                        │
├─────────────────────────────────────────────────────────────┤
│ 冲突标准   J-003 · 对外效果承诺必须附可核验来源（已确认，v2）    │
│ 历史依据   来自「项目介绍 v2」的修改：                          │
│            "保证让你的工作效率提升十倍" → "减少重复整理资料的时间" │
│            你当时确认：避免缺乏证据的效果承诺                    │
│ 建议       补充可核验来源；或改为限定条件表达，                  │
│            例如"在 X 场景下可减少约 Y 的整理时间（来源）"          │
├─────────────────────────────────────────────────────────────┤
│ [ 接受 ]  [ 拒绝 ▾ ]  [ 这次是例外 ]  [ 调整范围 ]              │
└─────────────────────────────────────────────────────────────┘
```

- 没有 `rule_id` 的发现用灰色"通用建议"标签，与蓝色"团队记忆"标签区分。
- 页面顶部指标条：`命中 5 · 接受 3 · 拒绝 1 · 例外 1 · 人工解释 2 次`（"人工解释"= 用户改写解释文本或新建规则的次数）。
- 复审页额外显示"与上一轮对比"：`重复问题 3 → 1 · 人工解释 2 → 0 · 接受率 60% → 80%`。

### 3.8 前端页面与交互状态

| 页面 | 输入 | 输出 | 状态 | 异常 |
|------|------|------|------|------|
| P0 工作区 | 选择品牌 A / B | 加载对应记忆文件 | 空 / 已加载 | 记忆文件损坏 → 提示并允许重置 |
| P1 导入 | 原稿、修改稿、场景标签 | 句级 diff | 空 / diff 中 / 完成 | 两稿完全相同 → 提示无差异；过长 → 截断提示 |

### 3.9 最小技术架构

```
浏览器（单页应用，React/Vite 或 Streamlit，选团队最熟的）
   │  REST
   ▼
后端（FastAPI / Node，单进程）
   ├─ /import        → diff（difflib 级别即可）→ 调 LLM 提取候选（结构化 JSON 输出）
   ├─ /confirm       → 写记忆（纯代码，不调模型）
   ├─ /review        → 代码按 scope+active 过滤规则 → 调 LLM 逐句审核（要求引用 rule_id）→ 校验 rule_id 存在
   ├─ /feedback      → 更新 stats / exceptions / scope / history（纯代码）
   ├─ /memory        → 读记忆
   └─ /log           → 读日志
   │
   ▼
存储：每个 workspace 一个 JSON 文件（brand_A.json / brand_B.json）+ 一个 append-only 的 log.jsonl
模型：单一 LLM API，两类调用（提取候选 / 逐句审核），温度低，要求 JSON schema 输出
```

**模型调用边界（重要）**
- 模型只做两件事：从 diff 归纳候选判断；按给定规则逐句审核并引用 rule_id。
- 模型不做：决定规则是否长期、决定范围、处理例外、更新记忆。这些全部是代码 + 用户动作。
- 这样答辩时可以明确说："学习闭环里模型只负责提出假设，人负责确认，代码负责记忆，三者边界清楚。"

**降级策略**
- 模型 API 超时：重试 1 次后，用最近一次成功结果 + 明确标注"缓存结果"，不伪装为实时。
- 现场无网：提前录屏一段真实运行作为备份，但答辩时如实说明是录屏。

## 5. 关键机制审核

| 机制 | 是否足以成立 | 现状判断 | 如何加强 |
|------|------------|---------|---------|
| **修改意图识别，而不是表面措辞模仿** | 有条件成立 | 思路文档设计了"二选一解释"，方向正确；但只靠模型一次归因仍可能出错 | ① 每条候选强制给出 ≥2 个互斥解释；② 每个解释附一个"如果选此项，下面这句会/不会被拦"的反例预演，让用户在确认时就能看到后果；③ 记录 `rejected_explanation`，作为过程记录素材 |
| **条件化规则，而不是全局禁词** | 可成立，取决于实现位置 | 文档有"公开宣传 vs 报名提醒"案例 | 范围过滤放在代码层（见 3.5），并在 UI 显示"本次审核加载了 N 条规则，跳过 M 条（范围不符）"，让评委看见过滤发生 |
| **用户可推翻错误推断** | 可成立 | 文档有"接受/拒绝/例外"设计 | 拒绝时 3 选 1 原因，分别触发不同更新路径；规则改版后旧版进入 `history[]`；UI 展示"v1 → v2 变更原因" |
| **依据可追溯** | 可成立 | 四段式展示已设计 | 后端校验模型引用的 rule_id 必须存在，否则降级为通用建议；evidence 直接展示 before/after 原文 |
| **例外不会污染长期标准** | 需要设计保证 | 文档提到但未说明机制 | 例外只写 `exceptions[]`，不改 `trigger`/`scope`；同场景例外 ≥2 次才提议范围变更；Demo 中标例外后立即再审一篇同类型公开宣传稿证明规则仍生效 |
| **同一文案在不同团队记忆下产生不同结果** | 可成立，但必须用真实数据 | 评分标准给出 A/B 设定 | A/B 记忆分别由两位队员的真实修改生成；不要手写规则填进去 |
| **使用次数增加后，人工解释成本下降** | 一天半只能证明趋势，不能证明规律 | 评分标准给出期望曲线 | 明确定义"人工解释"= 改写解释文本或新建规则的次数；逐轮自动记录；答辩中只报实际数字（如 3 → 1），不做百分比包装 |

**总体判断**：七个机制在设计层面都能成立，但目前全部停留在"文档描述"阶段。真正的分水岭是：**范围过滤、例外隔离、rule_id 校验、日志落盘这四件事是否做在代码层。** 做在代码层，就能反驳"提示词 + RAG"；只做在提示词里，就反驳不了。
