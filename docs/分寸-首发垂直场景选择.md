# 「分寸」首发垂直场景选择

> 生成日期：2026-09-12 · 阶段一产出
> 结论先行：**唯一首发场景 = AI 产品方案审查；唯一最小任务 = AI 产品指标与验收标准审查。**

---

## 1. 四个候选场景比较

评分：● 强 / ◐ 中 / ○ 弱 / ？ 无证据（按"无证据 = 不能依赖"处理）

| 比较维度 | AI PRD / AI 功能方案上线前审查 | AI Agent 方案审查 | 奢侈品报告或内容审查 | 建筑报告审查 |
|---------|------|------|------|------|
| 团队已有判断能力 | ● 团队全员是 AI 产品经理，评审 PRD 是日常工作 | ◐ 团队刚读完 Agent 蓝图，有方法论但实战判断有限 | ？ 材料无背书 | ？ 材料无背书 |
| 短时间内真实产生 ≥3 组原稿/修改稿 | ● 队员可现场写方案片段，另一人评审修改；且团队自己的「分寸」思路文档就是一组真实的方案→修改 | ◐ 可写，但 Agent 方案篇幅大、修改点分散 | ○ 需要真实报告样本，团队手头无 | ○ 同上，且涉及专业规范 |
| 目标用户能否由团队成员扮演 | ● 就是他们自己 | ◐ 可以，但"资深 Agent 架构评审人"身份存疑 | ○ 需奢侈品行业背景 | ○ 需建筑/结构专业背景 |
| 评委能否快速看懂 | ● 中客松评委多为 AI/产品背景，PRD 指标句一眼能懂 | ◐ 需要理解架构取舍 | ◐ 内容审查可懂，但"为什么这样改"需要行业语境 | ○ 评委无法判断审核结论是否正确 |
| 错误代价是否清晰 | ● 无基线的指标 → 上线后无法验收 → 项目返工；评审人对此有切身之痛 | ◐ 架构错误代价大但显现慢 | ◐ 品牌合规风险 | ● 安全代价极清晰，但团队无法证明自己判断对 |
| 判断是否有条件、范围、例外 | ● 天然有：上线前 PRD 要求基线，探索期方案允许方向性目标；内部工具不要求用户满意度指标 | ● 有（单 Agent vs 多 Agent 的条件） | ◐ 有，但团队不掌握 | ● 有，但团队不掌握 |
| Vibe Coding 可行性 | ● 纯文本、句级处理 | ● 纯文本 | ● 纯文本 | ◐ 可能涉及图纸/表格 |
| 多 Agent 是否真的必要 | ○ 不必要（这是好事） | ○ 不必要 | ○ 不必要 | ○ 不必要 |
| 一天半内完成风险 | ● 低 | ◐ 中（方案长、diff 噪声大） | ● 高（数据来源不可控） | ● 高 |
| 赛事评分匹配度 | ● 数据壁垒：两位 PM 评审标准天然不同；可用性：句级流程短；过程记录：误判易复现；持续价值：PM 反复评审 PRD 是真实高频 | ◐ | ○ 无真实数据 = 数据壁垒零分风险 | ○ 同上 |

### 结论

**选择 AI 产品方案审查。** 奢侈品和建筑两个场景在"团队判断能力"和"真实数据可得性"两项均为无证据，按新提示词前提 5，不得未经验证地纳入；作为未来扩展方向单列（见第 4 节）。AI Agent 方案审查的判断粒度偏架构层，不利于 3 分钟 Demo 的句级展示，且团队实战判断经验弱于 PRD 评审。

## 2. 在 AI 产品方案审查内继续收窄：五个最小任务比较

| 最小任务 | 判断是否句级可标注 | 不同评审人是否天然有差异 | 条件/范围/例外是否清晰 | 3 分钟 Demo 可展示性 | 现场产生数据的难度 |
|---------|------|------|------|------|------|
| AI PRD 上线前审查（整体） | ◐ 范围太宽，判断类型混杂 | ● | ◐ | ○ 一份 PRD 太长 | ◐ |
| AI Agent 方案审查 | ○ 判断在架构层，非句级 | ● | ● | ○ | ◐ |
| AI 功能需求真实性审查 | ◐ "用户是否真的需要"难以形成可验证规则 | ● | ○ 边界模糊 | ◐ | ◐ |
| **AI 产品指标与验收标准审查** | **●** 每条指标是一句话，可逐句标注 | **●** 有的评审人接受"显著提升"类方向性目标，有的要求每条指标有基线+测量方法+负责人 | **●** 上线前 PRD vs 探索期方案；面向用户 vs 内部工具；核心指标 vs 观察指标 | **●** 一段 10–15 句的指标章节即可 | **●** PM 写指标章节是日常动作，10 分钟一份 |
| AI 产品风险与异常场景审查 | ◐ 判断是"缺了什么"而非"这句有问题"，标注难度高 | ● | ◐ | ◐ | ◐ |

### 选定：**AI 产品指标与验收标准审查**

**选择理由：**

1. **判断是句级的，和「分寸」机制完全对齐。** "准确率提升至 95%"这一句，评审人 A 会改成"在 X 测试集上准确率从 87% 提升至 95%，由算法组每周测量"——这个修改和原思路里"提升十倍 → 减少重复整理时间"的结构一模一样：表面是加了数字/删了数字，实际判断是"效果承诺需要基线和测量方法"。
2. **错误归因的陷阱天然存在。** 系统很容易把上面这条学成"指标必须有百分比"或"不允许出现 95% 这种整数目标"，用户可以立刻用一句含有依据的指标推翻它——这正是 Demo 需要展示的"合理但错误的初始判断"。
3. **不同评审人的差异真实且可解释。** 一位 PM 可能坚持"探索期方案允许方向性目标"，另一位坚持"任何指标必须有负责人和验收时间"。同一句"用户满意度显著提升"在两套记忆下结论不同，且评委能立刻理解为什么。
4. **数据可在现场真实产生。** 每位队员 10 分钟能写一段指标章节；另一位 10 分钟能评审修改并写理由。3 组 × 2 位评审人 = 1 小时内完成。
5. **错误代价评委秒懂。** "没有基线的指标上线后无法验收"是所有产品人的共同经验。

**不选其他四项的一句话理由：**
- PRD 整体审查：范围太宽，一天半内规则类型会失控。
- Agent 方案审查：判断在架构层，无法逐句展示。
- 需求真实性审查：难以形成可被推翻的具体规则。
- 风险与异常审查：判断是"缺失检测"，与"修改轨迹提取"机制不匹配。

## 3. 首发场景的用户、输入、输出定义

| 项 | 定义 |
|----|------|
| 目标用户 | 负责 AI 产品方案上线评审的产品负责人（Demo 中由队员本人扮演，使用其本人真实修改） |
| 真实问题 | 每次评审 PRD 的指标章节，都要重新解释一遍"这个指标没有基线""这个目标没法验收""谁负责测"——这些判断有个人风格，写不进通用规范，交不给新人也交不给通用 AI |
| 输入（学习） | 一段 AI 产品方案的「指标与验收标准」章节原稿 + 评审人修改稿 + 逐条修改理由（可选，一句话）+ 文档场景标签（上线前 PRD / 探索期方案 / 内部工具方案） |
| 输入（审核） | 一段新的指标章节 + 场景标签 |
| 输出（学习） | ≤3 条候选判断，每条含 2 个互斥解释 + 反例预演 + 建议范围 + 来源片段 |
| 输出（审核） | 逐句：问题句 → 冲突规则（rule_id, 版本）→ 历史依据（来源修改 before/after + 用户确认的解释）→ 可执行建议 |
| 边界 | 只处理指标与验收标准章节（≤ 40 句）；不处理整份 PRD；不处理表格/图；不做自动改写全文 |

### 示例判断（仅为说明机制，**不是数据**，不得预置为规则）

| 原稿句 | 评审人修改 | 系统可能的两个解释 | 正确解释 | 反例预演 |
|-------|-----------|------|------|------|
| "模型准确率提升至 95%" | "在 2025Q3 标注测试集上，准确率从 87% 提升至 95%，算法组每周测量" | ① 效果指标必须附基线与测量方法 ② 不允许出现整数百分比目标 | ① | 若选①："在内部评测集上召回率从 60% 提升至 75%"通过，"召回率达到 75%"被拦；若选②：两句都被拦 |
| "用户满意度显著提升" | 探索期方案中保留；上线前 PRD 中改为"NPS 从 32 提升至 40，由用研组季度测量" | ① 禁止方向性表述 ② 上线前 PRD 的指标必须可测量，探索期允许方向性目标 | ② | 若选②：探索期方案中"显著提升"通过，上线前 PRD 中被拦 |
| "由业务方验收" | "由增长部张 X 于 11 月 30 日前验收" | ① 每条指标必须有具名负责人与时间 ② 不允许出现"业务方"一词 | ① | 若选①："由算法组于上线后两周内验收"通过（有部门+时间） |

## 4. 未来扩展方向（单列，**不得混入当前 MVP 定位和 Demo**）

- AI PRD 其他章节（风险与异常场景、需求真实性）
- AI Agent 方案审查（单/多 Agent 取舍、工具边界）
- 奢侈品报告/内容审查 —— 需要有行业背景的评审人和授权样本
- 建筑报告审查 —— 需要专业规范知识与合规审核
- 原方向：品牌文案审核 —— 机制相同，数据来源不同

答辩中如被问"能否迁移"，回答："机制通用，数据不通用——这正是赛道要求的。我们只验证了一个场景，不宣称其他场景已成立。"
