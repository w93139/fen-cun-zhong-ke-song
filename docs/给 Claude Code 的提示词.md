# 「分寸」中客松项目：给 Claude Code 的提示词

## 使用方式

在项目目录 `/Users/tan/Desktop/分寸` 中启动 Claude Code，然后先粘贴“总控提示词”。

如果希望逐步检查，就按“阶段提示词 1 → 5”的顺序发送。除非特别说明，Claude Code 只做分析和文档产出，不要直接编写产品代码。

## 一、总控提示词：先读材料，再完成整体审核与框架设计

```text
你现在是「分寸」中客松项目的首席产品策略师、AI 产品架构师和赛事评委模拟器。

你的任务不是简单总结材料，而是基于当前目录中的全部项目文件，审核项目思路，并形成一套可以用于开发、演示和答辩的整体框架。

请先读取并理解以下文件：
- 「分寸」：一个通过修改学会你工作标准的 AI 审稿搭档。.md
- 「分寸」与题目“做一个别人抄不走，自己也离不开的 AI 产品”是匹配的，但目前还需要把“为什么抄不走、为什么离不开”说得更硬。.md
- 评分标准说明.md
- 其他相关文件（如存在，也一并读取）

工作原则：
1. 严格区分“文档中已有的事实”“合理推断”“尚未验证的假设”，不要把假设写成事实。
2. 以赛事评分标准为最高约束，优先检查：数据壁垒、产品可用性、过程记录、持续使用价值。
3. 对“这是不是提示词 + 知识库”“修改稿是否真的代表标准”“用户是否愿意持续反馈”等问题进行红队式质疑。
4. 不要为了显得完整而添加多智能体、复杂账号系统、浏览器插件、企业集成等非必要功能。
5. 重点证明：同一输入在不同团队记忆下会得到不同结果；用户推翻错误判断后，系统之后会改变；第二次审核比第一次更少需要人工解释。
6. 如果资料不足，先列出缺口，并给出带有“待验证”标签的最小假设；不要虚构用户、数据、实验结果或技术能力。

请按以下结构输出，中文回答，结论先行：

### 1. 一页纸结论
- 项目当前最强的价值主张
- 当前最危险的 3 个问题
- 是否建议继续沿用当前方向
- 冲奖必须优先完成的 5 件事

### 2. 项目核心定位
用一句话分别写出：目标用户、核心痛点、产品承诺、独有数据、长期依赖理由。
同时给出一个“不要这样讲”的错误定位版本，并解释为什么会被评委认为只是通用 AI 审稿工具。

### 3. 端到端产品框架
覆盖以下部分：
- 用户与首个具体场景
- 真实输入与输出
- 核心用户旅程
- MVP 必须有、可以有、明确不做的功能
- 学习闭环：原稿/修改稿 → 候选判断 → 用户确认 → 新稿审核 → 接受/拒绝/例外 → 记忆更新
- 判断记忆的数据结构
- 条件、适用范围、例外、来源、时效和可撤销机制
- 审核结果的展示格式
- 前端页面或交互状态
- 后端/模型/存储的最小技术架构

### 4. 赛事评分标准映射表
用表格列出：评分维度、要证明的命题、当前已有证据、证据强度、缺口、现场演示动作、可记录指标。

### 5. 关键机制审核
逐项判断以下机制是否足以成立，并指出如何加强：
- 修改意图识别，而不是表面措辞模仿
- 条件化规则，而不是全局禁词
- 用户可推翻错误推断
- 依据可追溯
- 例外不会污染长期标准
- 同一文案在不同团队记忆下产生不同结果
- 使用次数增加后，人工解释成本下降

### 6. 现场 Demo 方案
设计一条可在比赛现场跑通的闭环，包含真实输入、每一步的界面/输出、用户动作、系统状态变化和评委能看到的证据。
至少包含：
1. 导入一组原稿和修改稿；
2. 系统提出候选判断；
3. 用户确认适用范围；
4. 审核新稿并展示历史依据；
5. 用户拒绝或标记一次例外；
6. 再审一篇新稿，证明系统已经改变且没有误伤例外。

### 7. 对照实验与指标
设计最小可行的对照：
- 基础模型裸审
- 只提供历史文案
- 使用「分寸」结构化判断记忆
说明每组输入、输出、评价者、指标和不能过度宣称的地方。

### 8. 答辩叙事
产出：
- 30 秒电梯陈述
- 3 分钟 Demo 讲解词
- 5 分钟答辩主线
- 评委可能追问的 10 个问题及建议回答

### 9. 红队结论
模拟最苛刻的评委，回答：
- 为什么不是提示词 + RAG？
- 为什么修改稿能代表长期标准？
- 用户为什么愿意持续反馈？
- 数据壁垒到底在哪里？
- 换一个团队后，结果如何实质变化？
- 如果模型判断错了，系统如何恢复？
- 一天半能否完成？

### 10. 最终行动清单
按“今天必须做 / 明天必须做 / 有时间再做”排序，并为每项标注：负责人角色、预计耗时、验收标准、失败止损点。

最后请把结果写入：
- `docs/分寸-项目总框架.md`
- `docs/分寸-问题与风险审计.md`
- `docs/分寸-Demo与答辩方案.md`

如果 `docs` 目录不存在可以创建。不要修改原始思路文档，不要编写应用代码。完成后告诉我新增了哪些文件，并指出其中仍然需要我确认的假设。
```

## 二、阶段提示词 1：对现有文档做“证据审计”

```text
请只做一次严格的文档与论证审计，不要设计新功能，也不要写代码。

读取当前目录中所有与「分寸」和比赛相关的文件，建立一张审计表，列出每个重要主张：
- 主张原文或准确转述
- 它属于事实、推断还是假设
- 对应哪个赛事评分维度
- 当前证据是什么
- 评委可能如何质疑
- 风险等级（高/中/低）
- 最小验证方式
- 建议保留、改写还是删除

重点审计：
1. “别人抄不走”的依据是否真的来自修改轨迹、判断理由、范围、例外和纠正，而不是普通知识库；
2. “自己也离不开”的依据是否能落到重复解释减少、人工审核负担下降；
3. 修改稿是否可能只是临时偏好、客户意见或事实纠错；
4. 是否清楚区分长期标准、项目规则、单次例外和暂不记录；
5. 是否有证据证明不同团队记忆会导致不同审核结果；
6. 是否有证据证明错误记忆能被推翻且不会污染后续判断。

最后输出：
- 当前最可信的 5 个论点；
- 最薄弱的 5 个论点；
- 必须补证的 5 个证据；
- 一段不超过 120 字的“经审核后核心定位”。
把结果写入 `docs/分寸-证据审计.md`。
```

## 三、阶段提示词 2：生成工程可执行的 MVP 总体框架

```text
基于已经完成的证据审计，设计「分寸」的一天半 MVP，不要扩张范围。

请输出一份工程可执行的总体框架，必须包括：
- 单一目标用户和单一首发场景；
- 一条从导入到复审的完整流程；
- 页面/组件清单及每个页面的输入、输出、状态和异常情况；
- 判断记忆的数据模型，至少包含：规则内容、触发条件、适用场景、来源版本、用户确认状态、例外、更新时间、有效性；
- 候选判断提取与冲突检测的模型调用边界；
- 接受、拒绝、例外、修改范围后如何更新记忆；
- 同一输入切换品牌 A / 品牌 B 记忆时如何产生可见差异；
- 最小测试数据集与测试用例；
- 必须做、可延后、明确不做的列表；
- 失败降级策略和演示前检查清单。

所有设计都要回答“它如何证明产品不是一次性生成规则”。
把结果写入 `docs/分寸-MVP产品与技术框架.md`。
```

## 四、阶段提示词 3：生成现场 Demo、路演和证据采集方案

```text
请把「分寸」设计成一场可见的学习过程，而不是功能菜单展示。

请产出：
1. 3 分钟 Demo 分镜：每 15–30 秒展示什么、输入什么、用户点击什么、系统状态怎样变化、评委应理解什么；
2. 一个合理但错误的初始判断，以及用户如何纠正它；
3. 纠正后同时包含“无依据数字”和“有依据数字”的新文案，证明系统学到的是条件而不是禁词；
4. 一次“公开宣传规则不适用于报名截止提醒”的例外演示；
5. 品牌 A / 品牌 B 同文案对照演示；
6. 现场需要记录的截图、日志、版本和指标；
7. Demo 失败时的备用路径，但不能伪装成现场实时结果；
8. 30 秒、90 秒、3 分钟三版项目叙事。

请明确区分：真实现场输入、预置样例、演示辅助数据。不要编造实验结果。
把结果写入 `docs/分寸-Demo与答辩方案.md`。
```

## 五、阶段提示词 4：以评委身份进行红队压力测试

```text
现在请完全站在中客松评委、技术评审和产品投资人的立场，对「分寸」做一次反方审查。

请提出至少 15 个尖锐问题，并按“致命 / 重要 / 可解释”分类。至少覆盖：
- 与提示词、RAG、普通审稿器的差异；
- 数据壁垒是否成立；
- 修改稿的代表性与噪声；
- 用户反馈成本；
- 规则冲突、例外污染和版本失效；
- 模型幻觉与错误归因；
- 隐私与敏感文案；
- 一天半 MVP 的可信度；
- 持续使用价值是否只是口号；
- 是否能迁移到其他团队而不失去个体差异。

每个问题都给出：
- 评委为什么会问；
- 当前最诚实的回答；
- 还缺什么证据；
- Demo 中如何用 30 秒证明；
- 如果无法证明，应该删掉或改写什么主张。

最后给出一个“是否建议参赛当前版本”的判断，不能只给鼓励。
把结果写入 `docs/分寸-红队压力测试.md`。
```

## 七、建议在 Claude Code 产出后追加的一条校准提示词

```text
请不要继续扩展方案。现在只做“主张—证据—演示动作”三列校准：

把最终方案中的每一个核心主张列出来，并为每个主张绑定一个现场可见的证据和一个具体演示动作。如果某个主张没有证据，标记为“删除、降级为假设或补验证”，不要用更华丽的文案掩盖证据不足。

特别检查：
- 是否把“记住规则”误写成“理解判断”；
- 是否把“有修改记录”误写成“有数据壁垒”；
- 是否把“用户可以反馈”误写成“用户会持续使用”；
- 是否把预置答案误写成实时能力；
- 是否把一次成功案例误写成普遍效果。
```
